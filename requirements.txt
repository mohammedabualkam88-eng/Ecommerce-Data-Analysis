# 1. טעינת נתונים — Data Loading

## 1.1 מטרת השלב

טעינת הנתונים היא השלב הראשון בתהליך ניתוח הנתונים. בשלב זה קוראים את קובצי המקור וממירים אותם למבני נתונים שניתן לעבד ולנתח באמצעות Python.

בפרויקט נעשה שימוש במאגר Olist, הכולל מספר טבלאות המתארות היבטים שונים של פעילות מסחר אלקטרוני.

בין הטבלאות המרכזיות:

| טבלה | תיאור |
|---|---|
| Customers | פרטי לקוחות ומזהים |
| Orders | הזמנות, סטטוסים ותאריכים |
| Order Items | פריטים שנכללו בהזמנות ומחיריהם |
| Payments | נתוני תשלומים |
| Products | פרטי מוצרים |
| Sellers | נתוני מוכרים |
| Reviews | ביקורות ודירוגי הזמנות |
| Geolocation | מידע גאוגרפי |
| Category Translation | תרגום שמות קטגוריות מוצרים |

## 1.2 שימוש בספריית Pandas

ספריית Pandas מאפשרת לקרוא קובצי CSV ולשמור אותם כאובייקטים מסוג DataFrame.

דוגמה:

```python
import pandas as pd

customers = pd.read_csv(
    "DATA/RAW/olist_customers_dataset.csv"
)

orders = pd.read_csv(
    "DATA/RAW/olist_orders_dataset.csv"
)

order_items = pd.read_csv(
    "DATA/RAW/olist_order_items_dataset.csv"
)
```

**הסבר הקוד:**

- `import pandas as pd` — מייבא את ספריית Pandas ומגדיר עבורה את הכינוי `pd`.
- `pd.read_csv()` — קורא נתונים מקובץ CSV.
- `customers` — שומר את טבלת הלקוחות.
- `orders` — שומר את טבלת ההזמנות.
- `order_items` — שומר את טבלת פריטי ההזמנות.

נתיבי הקבצים בדוגמה הם להמחשה ויש להתאימם למיקום ולשמות הקבצים בפרויקט.

## 1.3 חשיבות עסקית

טעינה נכונה של נתונים היא תנאי בסיסי לאמינות הניתוח. קובץ שלא נטען כראוי, עמודה שמפורשת בסוג נתונים שגוי או נתונים חסרים עלולים להשפיע על התוצאות העסקיות.

**תוצר השלב:** טבלאות נתונים הזמינות לניתוח באמצעות Pandas.

# 2. חקירת נתונים — Exploratory Data Analysis (EDA)

## 2.1 מטרת השלב

Exploratory Data Analysis הוא תהליך ראשוני של היכרות עם הנתונים.

המטרה היא להבין את מבנה הטבלאות, מספר הרשומות, סוגי המשתנים, איכות הנתונים והתפלגות הערכים.

לפני חישוב מדדים עסקיים, יש לוודא שהנתונים מתאימים לניתוח המתוכנן.

## 2.2 בדיקת מבנה הנתונים

```python
orders.head()
```

הפקודה `head()` מציגה את חמש הרשומות הראשונות כברירת מחדל.

באמצעותה ניתן לזהות את שמות העמודות, לבחון ערכים לדוגמה ולהבין את מבנה הנתונים.

```python
orders.shape
```

הפקודה `shape` מחזירה את מספר השורות והעמודות בטבלה.

```python
orders.info()
```

הפקודה `info()` מציגה מידע על העמודות, סוגי הנתונים ומספר הערכים שאינם חסרים.

```python
orders.describe()
```

הפקודה `describe()` מציגה מדדים סטטיסטיים תיאוריים עבור עמודות מספריות כברירת מחדל, כגון ממוצע, סטיית תקן, ערכי מינימום ומקסימום ורבעונים.

## 2.3 בדיקת ערכים חסרים

```python
orders.isnull().sum()
```

הפקודה בודקת כמה ערכים חסרים קיימים בכל עמודה.

לדוגמה, בטבלת הזמנות עשויים להופיע תאריכים חסרים עבור שלבי אספקה שטרם הושלמו או עבור הזמנות שבוטלו.

לכן, ערך חסר אינו בהכרח שגיאה. לעיתים הוא מייצג מצב עסקי תקין.

## 2.4 בדיקת כפילויות

```python
orders.duplicated().sum()
```

הפקודה מחזירה את מספר השורות הזהות לחלוטין.

עם זאת, חשוב להבחין בין כפילות של רשומה לבין הופעה חוזרת לגיטימית של מזהה הזמנה בטבלת פריטי הזמנות.

הזמנה אחת עשויה להכיל מספר פריטים, ולכן אותו `order_id` יכול להופיע מספר פעמים בטבלת `order_items`.

## 2.5 חשיבות עסקית

EDA מאפשר לזהות בעיות לפני שהן משפיעות על חישובי הכנסות, מספר לקוחות או תדירות רכישה.

**תוצר השלב:** הבנה ראשונית של מבנה הנתונים, איכותם והמגבלות שיש להביא בחשבון בהמשך הניתוח.

# 3. ניקוי נתונים — Data Cleaning

## 3.1 מטרת השלב

ניקוי נתונים נועד לשפר את איכות המידע ולהבטיח שהניתוחים יתבססו על נתונים עקביים, רלוונטיים ואמינים.

הפעולות האפשריות כוללות טיפול בערכים חסרים, בדיקת כפילויות, המרת סוגי נתונים, בדיקת תאריכים וזיהוי ערכים חריגים.

## 3.2 טיפול בערכים חסרים

```python
orders.isna().sum()
```

לאחר זיהוי ערכים חסרים יש להחליט כיצד לטפל בהם.

אפשרויות נפוצות:

- השארת הערך החסר כאשר הוא בעל משמעות עסקית.
- הסרת רשומות כאשר לא ניתן להשתמש בהן בניתוח מסוים.
- השלמת ערכים כאשר קיימת הצדקה מתודולוגית ברורה.
- יצירת אינדיקטור המייצג היעדר מידע.

אין להסיר אוטומטית את כל הרשומות הכוללות ערכים חסרים, משום שפעולה כזאת עלולה לגרום לאובדן מידע משמעותי.

## 3.3 המרת תאריכים

```python
orders["order_purchase_timestamp"] = pd.to_datetime(
    orders["order_purchase_timestamp"],
    errors="coerce"
)
```

**הסבר:**

- `pd.to_datetime()` ממירה ערכים לפורמט תאריך ושעה.
- `errors="coerce"` ממירה ערכים שאינם ניתנים לפענוח ל-`NaT`.

המרת תאריכים חיונית לניתוחים המבוססים על זמן, במיוחד לחישוב Recency במסגרת RFM.

## 3.4 בדיקת כפילויות לפי מפתח

```python
orders["order_id"].duplicated().sum()
```

בדיקה זו מאפשרת לזהות הופעות חוזרות של מזהי הזמנה בטבלת ההזמנות.

לפני הסרת כפילויות יש להבין את רמת הפירוט של כל טבלה ואת משמעות המפתח שלה.

## 3.5 בדיקת ערכים חריגים

ערכים חריגים עשויים להופיע במחירי מוצרים, במספר פריטים להזמנה או בערכים כספיים.

לא כל ערך חריג הוא שגוי. רכישה בעלת סכום גבוה עשויה להיות עסקה אמיתית של לקוח בעל ערך גבוה.

לפיכך, יש להבחין בין שגיאת נתונים לבין תופעה עסקית משמעותית.

## 3.6 חשיבות עסקית

נתונים שאינם נקיים עלולים לגרום להערכת יתר של מכירות, לספירה שגויה של לקוחות ולחלוקה לא מדויקת של קבוצות לקוחות.

**תוצר השלב:** נתונים שעברו בדיקות איכות ומתאימים לחישובים האנליטיים שנבחרו.

# 4. מיזוג טבלאות — Data Merging

## 4.1 מטרת השלב

מאגר Olist בנוי ממספר טבלאות מקושרות.

כדי לנתח את הקשר בין לקוחות, הזמנות ומכירות, יש לשלב מידע מטבלאות שונות.

הפעולה מתבצעת באמצעות `merge()` בספריית Pandas.

## 4.2 הקשרים בין הטבלאות

הקשרים המרכזיים כוללים:

- `customers.customer_id` מול `orders.customer_id`.
- `orders.order_id` מול `order_items.order_id`.
- `orders.order_id` מול `payments.order_id`.
- `order_items.product_id` מול `products.product_id`.

חשוב להבין שלא כל קשר הוא מסוג אחד-לאחד.

לדוגמה, הזמנה אחת עשויה לכלול מספר פריטים וגם מספר רשומות תשלום.

## 4.3 דוגמה למיזוג

```python
orders_customers = orders.merge(
    customers,
    on="customer_id",
    how="left"
)
```

**הסבר הקוד:**

- `orders.merge()` מבצע מיזוג בין שתי טבלאות.
- `on="customer_id"` מגדיר את העמודה המשותפת.
- `how="left"` שומר את כל הרשומות מהטבלה השמאלית ומצרף נתונים תואמים מהטבלה הימנית.

דוגמה נוספת:

```python
sales_data = orders_customers.merge(
    order_items,
    on="order_id",
    how="inner"
)
```

בדוגמה זו משולבים נתוני הזמנות ולקוחות עם נתוני פריטי ההזמנות.

## 4.4 מניעת ספירה כפולה

זהו אחד הנושאים החשובים ביותר בפרויקט.

אם הזמנה כוללת שלושה מוצרים, היא עשויה להופיע בשלוש שורות בטבלת פריטי ההזמנות.

לכן, חישוב מספר ההזמנות באמצעות מספר השורות עלול להציג תוצאה שגויה.

במקום זאת ניתן להשתמש ב:

```python
total_orders = sales_data["order_id"].nunique()
```

הפקודה `nunique()` סופרת ערכים ייחודיים בלבד.

יש להיזהר במיוחד ממיזוג ישיר בין טבלאות בעלות קשר אחד-לרבים משני הצדדים, כגון פריטים ותשלומים, משום שמיזוג כזה עלול להכפיל סכומים.

## 4.5 חשיבות עסקית

מיזוג נכון מאפשר לנתח הכנסות ברמת לקוח, לזהות דפוסי רכישה ולהפיק מדדים עסקיים אמינים.

**תוצר השלב:** טבלת ניתוח משולבת, שבה רמת הפירוט והקשרים בין הרשומות מוגדרים באופן ברור.

מדד זה מייצג את סכום מכירות המוצרים בהתאם להגדרה ששימשה בניתוח.

# 6. ניתוח RFM — Recency, Frequency, Monetary

## 6.1 מטרת השלב

RFM Analysis היא שיטה לניתוח התנהגות לקוחות באמצעות שלושה ממדים:

| מדד | משמעות |
|---|---|
| Recency | כמה זמן עבר מאז הרכישה האחרונה |
| Frequency | כמה רכישות ביצע הלקוח |
| Monetary | מהו הערך הכספי המצטבר של רכישות הלקוח |

השיטה מאפשרת לזהות קבוצות לקוחות בעלות דפוסי רכישה שונים.

## 6.2 חישוב Recency

Recency מודד את מספר הימים שעברו בין תאריך ייחוס לבין הרכישה האחרונה של הלקוח.

דוגמה:

```python
rfm["recency"] = (
    reference_date - rfm["last_purchase"]
).dt.days
```

ככל שהערך נמוך יותר, כך הרכישה האחרונה של הלקוח קרובה יותר לתאריך הייחוס.

חשוב שתאריך הייחוס יוגדר בהתאם לתקופת הנתונים ולא באופן שרירותי.

## 6.3 חישוב Frequency

Frequency מודד את מספר ההזמנות הייחודיות שביצע כל לקוח.

דוגמה:

```python
frequency = sales_data.groupby(
    "customer_unique_id"
)["order_id"].nunique()
```

השימוש ב-`nunique()` מונע ספירה חוזרת של הזמנות הכוללות מספר פריטים.

## 6.4 חישוב Monetary

Monetary מייצג את הערך הכספי המצטבר של רכישות הלקוח.

דוגמה:

```python
monetary = sales_data.groupby(
    "customer_unique_id"
)["price"].sum()
```

הגדרת המדד חייבת להיות עקבית עם הגדרת המכירות בפרויקט.

## 6.5 יצירת ציוני RFM

ניתן להמיר את שלושת המדדים לציונים יחסיים, למשל בטווח 1–5.

לקוחות בעלי Recency נמוך, Frequency גבוה ו-Monetary גבוה נחשבים בדרך כלל לבעלי פעילות וערך גבוהים.

בפרויקט מופיעות קבוצות לקוחות כגון:

- Champions — לקוחות בעלי ביצועים גבוהים לפי כללי הפילוח.
- Loyal Customers — לקוחות בעלי דפוס רכישה חוזר.
- At Risk — לקוחות בעלי סימנים אפשריים לירידה בפעילות.
- High Value New — לקוחות חדשים יחסית בעלי ערך רכישה גבוה.
- Recent Customers — לקוחות שביצעו רכישה לאחרונה.
- Other Customers — לקוחות שאינם משתייכים לקבוצות האחרות.

השיוך המדויק לקבוצות תלוי בספי הציונים ובכללי הסיווג שהוגדרו בקוד.

## 6.6 חשיבות עסקית

RFM מאפשר להתאים פעולות שיווק לקבוצות שונות.

# 8. ניתוח ריכוז הכנסות — Revenue Concentration & Pareto Analysis

## 8.1 מטרת השלב

ניתוח ריכוז הכנסות בוחן איזה חלק מסך ההכנסות נוצר על ידי קבוצות הלקוחות בעלות ההוצאה הגבוהה ביותר.

הניתוח מאפשר לזהות עד כמה העסק תלוי בקבוצה מצומצמת יחסית של לקוחות.

## 8.2 תהליך החישוב

ראשית, מחשבים את ההוצאה הכוללת של כל לקוח.

לאחר מכן ממיינים את הלקוחות בסדר יורד לפי ההוצאה.

לבסוף מחשבים את חלקם המצטבר בהכנסות עבור שיעורים שונים של לקוחות.

דוגמה למיון:

```python
customer_revenue = customer_revenue.sort_values(
    "total_sales",
    ascending=False
)
```

דוגמה לחישוב שיעור ההכנסות המצטבר:

```python
customer_revenue["cumulative_revenue_share"] = (
    customer_revenue["total_sales"].cumsum()
    / customer_revenue["total_sales"].sum()
    * 100
)
```

## 8.3 תוצאות הפרויקט

| Top 5% | 29.13% |
| Top 10% | 41.10% |
| Top 20% | 56.62% |

## 8.4 בחינת עקרון Pareto

עקרון Pareto מוכר גם ככלל 80/20, שלפיו במצבים מסוימים כ-80% מהתוצאות נובעות מכ-20% מהגורמים.

עם זאת, מדובר בכלל אצבע ולא בחוק מחייב.

בנתוני הפרויקט, 20% מהלקוחות המובילים אחראים לכ-56.62% מההכנסות.

לכן, **הנתונים אינם מציגים חלוקה קלאסית של 80/20**.

## 8.5 משמעות עסקית

הנתונים מצביעים על ריכוז הכנסות משמעותי, אך לא קיצוני בהתאם לכלל 80/20.

העסק עשוי להפיק תועלת מפעולות לשימור לקוחות בעלי ערך גבוה, ובמקביל מהרחבת בסיס הלקוחות הפעילים.

**תוצר השלב:** טבלת ריכוז הכנסות ותרשימים המציגים את שיעור ההכנסות המצטבר לפי קבוצות לקוחות.

# 11. ניתוח מגמות מכירה — Sales Trends Analysis

## 11.1 מטרת הניתוח

מטרת ניתוח מגמות המכירה היא לבחון את התפתחות ההכנסות ומספר ההזמנות לאורך זמן, לזהות חודשים בעלי ביצועים חריגים ולהעריך שינויים בפעילות העסקית.

הניתוח מבוסס על נתוני מכירות חודשיים וכולל השוואות Month-over-Month (MoM) ו־Year-over-Year (YoY).

## 11.2 הכנת נתונים חודשיים

נתוני ההזמנות והמכירות קובצו לפי חודש באמצעות Python ו־Pandas.

## 11.3 תוצאות מרכזיות

בניתוח נכללו 23 חודשים, עם הכנסות מצטברות של R$ 13,221,498.11.

החודש בעל ההכנסות הגבוהות ביותר היה **נובמבר 2017**, עם הכנסות של **R$ 987,765.37**.

זוהו גם חודשים בעלי פעילות נמוכה במיוחד, ובהם ספטמבר ודצמבר 2016. חודשים אלה דורשים זהירות בפרשנות של שיעורי צמיחה.

## 11.4 ניתוח צמיחה חודשית — MoM

מדד Month-over-Month Growth מודד את השינוי היחסי בהכנסות לעומת החודש הקודם.

הנוסחה:

**MoM Growth (%) = ((Current Month Revenue / Previous Month Revenue) − 1) × 100**

בניתוח נבדקה גם רציפות החודשים, כדי להימנע מהשוואה שגויה בין חודשים שאינם עוקבים.

כאשר אין חודש קודם מתאים, אין להציג שיעור צמיחה כאילו מדובר בהשוואה חודשית תקינה.

## 11.5 ניתוח צמיחה שנתית — YoY

מדד Year-over-Year Growth משווה את הכנסות החודש להכנסות החודש המקביל בשנה הקודמת.

**YoY Growth (%) = ((Current Month Revenue / Same Month Previous Year Revenue) − 1) × 100**

כדי לשפר את אמינות הניתוח, הוגדרו שלוש קטגוריות איכות:

- **Standard Comparison:** השוואה שנתית תקינה בהתאם לכללי הניתוח.
- **Low Base:** בסיס השוואה נמוך העלול להוביל לשיעורי צמיחה חריגים.
- **No Comparison:** אין נתונים מתאימים להשוואה שנתית.

סיווג זה מאפשר להבחין בין צמיחה עסקית משמעותית לבין תוצאה מספרית שעלולה להיות מטעה.
